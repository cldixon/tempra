# CLAUDE.md

## Spec
The source of truth for Tempra's design, decisions and current state is the Tempra library
**`cl_dixon/tempra-dev`**, read and written over the Tempra MCP tools (`start` with
`library: "cl_dixon/tempra-dev"`). Its `guide.md` says what belongs there; `v2/` is the managed
service as built, `delivery/` is CI/CD, `decisions/` records why, `process/workflow.md` is how a
change goes from a Linear issue to production. Read the concepts a feature touches before starting
on it. When implementation shows a concept is wrong, update the concept first, then the code.

OKF semantics, the store, the ledger and the MCP tools are still specified in the v1 Claude Doc,
**OKF Knowledge Service — Spec** (https://claude.ai/artifact/KMuKyyFBSJHzukyEGqvUDn), until they are
carried over. The v2 Claude Doc is retired (carried over at rev 20). There is no markdown copy of
either in this repo; do not add one.

## UI
The app and the landing page share one design system, `design/` (`@tempra/design`, TEMPRA-8): tokens as CSS custom properties (`--tempra-*`, light and dark through `light-dark()`), a base stylesheet and `.prose` for rendered markdown. Edit `design/src/*.css`, then `bun run build` in `design/` to regenerate `design/dist/` (committed; a test fails if it is stale). The app serves it at a hashed path (`/_design/tempra.<hash>.css`, `style-src 'self'`) and links it from every page; the site imports `@tempra/design/tempra.css`. Visual changes go in the package, not in either consumer.

Minimal and barebones first, in the app and on the site (spec: tempra-dev `v2/design-system.md`, UI rule). This is about styling, not technology: light neutral surfaces, dark text, clear links, pill buttons for actions, no design flourish and no colour until the palette (TEMPRA-1), and as little text as works (headings, labels, links, short sentences), so the bones of what we build stay visible. Scripts, TypeScript, React components and client-side state are fine where a page needs them; the app is becoming a React SPA (TEMPRA-9). Every visual decision comes from `@tempra/design` (tokens, base CSS, and layout primitives and components as they are needed); neither consumer adds styling beyond its own page layout, and nothing is styled inline. The look comes from a separate design effort (TEMPRA-1) working in the package.

The app is a React SPA, `app/` (`@tempra/app`, TEMPRA-9, TEMPRA-14). Every page (library list, directory, concept, attachment, activity, ledger, the library's settings, inbox, and the account's welcome, agents, invitations and account pages) is one shell from the Worker (`worker/src/ui/spa.ts`): the design stylesheet, the bundle at a hashed path (`/_app/app.<hash>.js`, immutable; code-split, so what only some pages need, Pele for diagrams, is a chunk beside it at `/_app/<name>-<hash>.js`, fetched on first use) and an empty root, under a CSP of `script-src 'self'` and `style-src 'self'` (the nonce went with Wordgard, TEMPRA-99; the reader's popovers get their coordinates through the CSSOM, which CSP leaves alone); no inline scripts or styles. The server still checks sign-in and, for library pages, `authorizeLibrary` before answering with the shell, and puts the account's theme (System, Light or Dark, TEMPRA-113) on the shell's root as `data-theme`, which sets `color-scheme` so the tokens' `light-dark()` values follow it with no flash. The SPA reads everything from the REST API with the session cookie (writes pass `fromThisSite`); `useLoad` (`app/src/api.ts`) keeps what each page loaded (the last 100), so a page seen before draws at once and is checked again in the background, changing only if the answer did, and a concept is prefetched when hovered in the tree or selected in the switcher (`prefetch.ts`); `GET …/files/{path}` with `Accept: application/json` describes any file (a concept with its frontmatter and body as a tree, a synthesized file's tree, an attachment's size and type). People read and comment; only agents write (TEMPRA-99, tempra-dev `decisions/read-and-comment-only.md`): there is no editor in the app, and `PUT …/files/{path}` stays for agents, scripts and the API. Three things stay server-rendered on purpose, as security-critical pages that must work with no script: sign-in and, while sign-up is by invite, Request access (`signin.ts`, `/request-access`, the one way onto the waitlist, TEMPRA-125), app consent (`/authorize`, `oauth/`) and the email-change link (`/account/email/confirm`); they and the Worker's error pages share one shell (`page()` in `oauth/pages.ts`: the public pages' frame from `design/src/public.css`, as the landing page has it: the ground, the wordmark, the page as a sheet, terms and privacy at the foot) from the design stylesheet alone, on the system theme, with the same headers (`PAGE_HEADERS`: no script, no framing, `no-store`, `noindex`) and a link onward from every dead end (TEMPRA-136). An unknown address or an uncaught error is such a page (404 or 500) when the request accepts HTML and is not a machine endpoint (`wantsPage`: `/api`, `/mcp`, OAuth's endpoints, downloads, static files keep JSON). Consent folds the folder limit and the connection's actor under More options, offers "Not you? Sign out" (back to the same consent), and refuses "Create libraries" with Read only or File tools only rather than dropping it; the email-change link only looks its link up on GET, and signed out says to sign in with the account's current email first (tempra-dev `v2/accounts.md`, `v2/connections.md`). Downloads (raw markdown, attachments, exports) are server routes too. Account management is in the API (`account-api.ts`: account, theme, sessions, email, handle, delete, connected apps), for a signed-in session only, never a token. Terms and privacy live on the landing page (`tempra.dev/terms`, `/privacy`); the app's old URLs redirect there.

The landing page (`site/`) is Astro: semantic HTML, the design package alone (the public pages' frame and the landing page's sections are `design/src/public.css`, TEMPRA-110; the site has no stylesheet of its own; its fonts are the package's Inter, bundled by the build), no third-party fonts or scripts.

## Tooling
- **bun for everything JS/TS**: installing (`bun install`, `bun add`), scripts (`bun run …`), tests (`bun test`), one-off binaries (`bunx`). Do not use npm, npx, yarn or pnpm, and do not commit other lockfiles.
- **TypeScript only** on the server (Worker + Durable Object). No Rust or WASM in v1.
- **Biome** for lint and format (`biome.json`); no ESLint or Prettier.
- **cf** (Cloudflare's CLI, beta, pinned) is a dev dependency of `worker/`; run it with `bunx cf …` from `worker/`. The Worker is configured in `worker/cloudflare.config.ts`; there is no `wrangler.jsonc`. To find a command, use `bunx cf cli search "<task>"` (anonymous wording: no names or IDs), then `--help` on the match or `bunx cf schema <command>`; do not walk nested `--help`. cf resource commands take IDs, not names or bindings (scripts/cf.ts reads the D1 ID from the config). Set `CF_SEND_TELEMETRY=false` in scripts and CI. Scripts call cf through `scripts/cf.ts` (async): cf (beta) sometimes prints its result and then never exits (a confirmation prompt keeps it alive, e.g. `d1 migrations apply`), so the helper accepts a complete JSON result once cf goes quiet, and otherwise times out and retries; keep calls made through it safe to repeat.
- **wrangler** stays a dev dependency only as the bundler `cf dev`/`cf build` delegate to (`worker/wrangler.config.ts`). Use Wrangler directly only for what cf lacks: live logs (`bunx wrangler tail tempra`).
- **The site is the exception:** `site/` is configured with `site/wrangler.jsonc`, because Cloudflare Workers Builds (which deploys it and posts PR previews) reads a Wrangler config. It has no bindings or data.

## Cloudflare
- `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are set in the cloud environment; cf (and wrangler) read them automatically.
- Remote resources: Worker `tempra` on `app.tempra.dev` (custom domain; `workers.dev` is off), D1 `tempra-accounts` (id in `cloudflare.config.ts`), R2 bucket `tempra-blobs`, KV `tempra-oauth`, Queue `tempra-sweep` (binding `SWEEP_QUEUE`, the blob sweep's fan-out, sent and consumed by the Worker; no dead-letter queue, TEMPRA-81). Do not create or delete remote resources without asking.
- Tokens and libraries are managed at `/agents` and `/` (or `/api/v1/tokens` and `/api/v1/libraries` with a `human:` token). `bun run seed --remote` (from `worker/`) still creates a library and token directly in the deployed D1.
- KV `tempra-oauth` (binding `OAUTH_KV`) holds OAuth clients and grants. The UI signs people in by email link only (Access was removed at the A4 cut-over); `SIGNUP` (a config var: `invite` in production and staging) decides who may create an account, and `bun run admin invite` manages the list. Local dev uses `DEV_SIGNIN=1` and `SIGNUP=open` from `worker/.dev.vars` (copy `worker/.dev.vars.sample`): sign-in links show on the page for localhost.
- `cloudflare.config.ts` is a function of `--mode`: production by default, `staging` for a separate Worker (`tempra-staging` on `staging.tempra.dev`) with its own D1 `tempra-accounts-staging`, R2 `tempra-blobs-staging`, KV `tempra-oauth-staging`, Queue `tempra-sweep-staging`, metering to `tempra_usage_staging` and rate-limit namespaces 2001, 2002 and 2003 (TEMPRA-76), and `preview` for PR N (`previewDeployment`: `tempra-pr-N` on `pr-N.tempra.dev` with `-pr-N` resources (Queue `tempra-sweep-pr-N` too), ids from `TEMPRA_PR`, `TEMPRA_PREVIEW_D1_ID`, `TEMPRA_PREVIEW_KV_ID`; no cron; metering to `tempra_usage_preview`, rate-limit namespaces 3001, 3002 and 3003). Scripts pick the mode from `TEMPRA_MODE`. With no mode (`cf dev`, `cf workers types`, a bare dry run) no custom domain is attached; `bun run deploy` defaults to `--mode production`.
- Mail goes through Cloudflare Email Service: the `EMAIL` binding is added only when `mailFrom` is set for a deployment in `cloudflare.config.ts`, which needs a sending domain onboarded in Cloudflare. Production sends from `noreply@mail.tempra.dev` (`mail.tempra.dev` is onboarded); local dev with `DEV_SIGNIN=1` still shows links on the page instead of mailing them. `OPERATOR_EMAIL` (a Worker secret, so the address stays out of the repo) receives the daily digest and a notice when someone new joins the waitlist (at most 10 a day), and is the only account that can open `/waitlist` to approve or dismiss them.
- Rate limits are `WRITE_LIMITER` (60 writes a minute per account), `REQUEST_LIMITER` (600 requests a minute per token or app) and `SESSION_LIMITER` (`SESSION_REQUESTS_PER_MINUTE` in `cloudflare.config.ts` per browser session, keyed by the session's stored hash: every page, API call and feed upgrade made with the cookie and no token, static files aside; TEMPRA-80; the gate fails if a busy browse uses over a quarter of it), production's on namespaces 1001, 1002 and 1003 (namespaces are account-wide, so each deployment has its own; `worker/test/config.test.ts` checks none is shared). Over a limit is a 429 with `Retry-After`; the SPA waits it out quietly (`api.ts`: reads retry, prefetches skip, what is shown stays); metering writes to the Analytics Engine dataset `tempra_usage`; storage per library is `LIBRARY_STORAGE_MB`.
- The landing page is the Worker `tempra-site` on `tempra.dev` and `www.tempra.dev` (www redirects to the apex). Cloudflare Workers Builds, connected to this repository with root directory `site`, deploys it: `main` runs `wrangler deploy`, other branches run `wrangler preview`, which posts a Preview URL and one per commit on the PR. It does not go through the app's preview/staging/production jobs.
- Naming: the product is Tempra (repository `cldixon/tempra`, `tempra.dev`); OKF names only the file format. The former `okf-service` Workers and their resources were moved and deleted (v2 spec: Move to tempra.dev). Don't introduce `okf-tool`/`okf-service` names.
- `worker/` is the deployable project and must stay self-contained: its own `package.json` with every dependency, nothing imported from outside `worker/` at build time except the `@tempra/design`, `@tempra/app` and `@tempra/editor` workspace packages (the Worker imports only `@tempra/editor/doc`) (CI's standalone job builds `worker/` with `design/`, `editor/` and `app/` alone; `bun install` builds the app's bundle). Nothing in the repository imports Wordgard any more (TEMPRA-99). `site/` takes the same package as `file:../design`, so Workers Builds must watch `design/*` as well as `site/*`. `cloudflare.config.ts` must not import Worker code (scripts import it under bun).

## CI
`.github/workflows/ci.yml` runs on PRs and pushes to `main`: `bun run check`, `bun run gate` (cf dev, sample-bundle round-trip, UI pages, the SPA and its reader in Chromium, MCP smoke), and a standalone build of `worker/` copied with `design/`, `editor/` and `app/` (`cf deploy --dry-run`). All must pass before merging.

CD (tempra-dev: `delivery/ci-cd.md`) runs after those three, each stage off until its repository variable is `on`:
- `PREVIEWS`: the `preview` job brings up PR N's preview and comments its URL; `preview-cleanup.yml` tears it down when the PR closes and sweeps leftovers nightly.
- `STAGING_DEPLOYS`: every push to `main` deploys staging and checks it (`/healthz`, MCP smoke with secret `STAGING_MCP_TOKEN` if set).
- `PRODUCTION_DEPLOYS`: then production in the same run, with no approval step (tempra-dev: `decisions/production-without-approval.md`); the GitHub Environment `production` has no required reviewer, and adding one would bring the step back.
- Each push to `main` runs on its own (TEMPRA-18): one run never blocks the next, and deploy jobs deploy only the tip of `main` (a superseded commit skips itself).

The `site/ builds` job checks, tests and builds the landing page; its previews and deploys come from Workers Builds.

Secrets: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `PREVIEW_EMAIL` (the operator, seeded as each preview's account), optional `STAGING_MCP_TOKEN`, `PRODUCTION_MCP_TOKEN` (read-only smoke), optional `ANTHROPIC_API_KEY` (only the preview job's `preview up` step sees it, and sets it on the `tempra-pr-N` Worker as a secret through Cloudflare's API; the managed-agent spike, TEMPRA-67), optional `PREVIEW_SEED_TOKEN` (a read-only token on the seed library, only for the `preview up` step, with repository variables `PREVIEW_SEED_LIBRARY` and optional `PREVIEW_SEED_URL`; TEMPRA-109).
