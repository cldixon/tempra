# CLAUDE.md

## Spec
The source of truth for Tempra's design, decisions and current state is the Tempra library
**`cl_dixon/tempra-dev`**, read and written over the Tempra MCP tools (`start` with
`library: "cl_dixon/tempra-dev"`). Its `guide.md` says what belongs there; `v2/` is the managed
service as built, `delivery/` is CI/CD, `decisions/` records why, `process/workflow.md` is how a
change goes from a Linear issue to production. Read the concepts a feature touches before starting
on it. When implementation shows a concept is wrong, update the concept first, then the code.

OKF semantics, the store, the ledger and the MCP tools are still specified in the v1 Claude Doc,
**OKF Knowledge Service — Spec** (https://claude.ai/artifact/KMuKyyFBSJHzukyEGqvUDn), until they are
carried over. The v2 Claude Doc is retired (carried over at rev 20). There is no markdown copy of
either in this repo; do not add one.

## UI
The app and the landing page share one design system, `design/` (`@tempra/design`, TEMPRA-8): tokens as CSS custom properties (`--tempra-*`, light and dark through `light-dark()`), a base stylesheet and `.prose` for rendered markdown. Edit `design/src/*.css`, then `bun run build` in `design/` to regenerate `design/dist/` (committed; a test fails if it is stale). The app serves it at a hashed path (`/_design/tempra.<hash>.css`, `style-src 'self'`) and links it from every page; the site imports `@tempra/design/tempra.css`. Visual changes go in the package, not in either consumer.

Minimal and barebones first, in the app and on the site (spec: tempra-dev `v2/design-system.md`, UI rule). This is about styling, not technology: light neutral surfaces, dark text, clear links, pill buttons for actions, no design flourish and no colour until the palette (TEMPRA-1), and as little text as works (headings, labels, links, short sentences), so the bones of what we build stay visible. Scripts, TypeScript, React components and client-side state are fine where a page needs them; the app is becoming a React SPA (TEMPRA-9). Every visual decision comes from `@tempra/design` (tokens, base CSS, and layout primitives and components as they are needed); neither consumer adds styling beyond its own page layout, and nothing is styled inline. The look comes from a separate design effort (TEMPRA-1) working in the package.

The app is a React SPA, `app/` (`@tempra/app`, TEMPRA-9, TEMPRA-14). Every page (library list, directory, concept, attachment, activity, ledger, diff, work queue, the library's settings, inbox, and the account's welcome, connect, tokens, connected apps, invitations and account pages) is one shell from the Worker (`worker/src/ui/spa.ts`): the design stylesheet, the bundle at a hashed path (`/_app/app.<hash>.js`, immutable; code-split, so what only some pages need, Pele for diagrams, is a chunk beside it at `/_app/<name>-<hash>.js`, fetched on first use) and an empty root, under a CSP of `script-src 'self'` and `style-src 'self'` (the nonce went with Wordgard, TEMPRA-99; the reader's popovers get their coordinates through the CSSOM, which CSP leaves alone); no inline scripts or styles. The server still checks sign-in and, for library pages, `authorizeLibrary` before answering with the shell, and puts the account's theme (System, Light or Dark, TEMPRA-113) on the shell's root as `data-theme`, which sets `color-scheme` so the tokens' `light-dark()` values follow it with no flash. The SPA reads everything from the REST API with the session cookie (writes pass `fromThisSite`); `useLoad` (`app/src/api.ts`) keeps what each page loaded (the last 100), so a page seen before draws at once and is checked again in the background, changing only if the answer did, and a concept is prefetched when hovered in the tree or selected in the switcher (`prefetch.ts`); `GET …/files/{path}` with `Accept: application/json` describes any file (a concept with its frontmatter and body as a tree, a synthesized file's tree, an attachment's size and type). People read and comment; only agents write (TEMPRA-99, tempra-dev `decisions/read-and-comment-only.md`): there is no editor in the app, and `PUT …/files/{path}` stays for agents, scripts and the API. The former Wordgard editor (TEMPRA-15) is in git history: the last commit on `main` that has it is `97175922c8633fb8ed4715e8221a6dac8c07fd04`; if human editing returns, it comes back as its own mode built from there. Concept bodies are drawn by the reader (tempra-dev `app/reader.md`; `app/src/Reader.tsx`, `app/src/reader/`): the stored tree rendered as React elements (`reader/Body.tsx`; nothing parsed, no HTML injected, links by the server's rules with unsafe schemes dropped, raw constructs shown as their markdown), every block with its ID as `data-block`, every textblock with its offset in `docText` as `data-text`, atoms (footnote markers, images, raw inline, hard breaks) marked `data-atom` and counted as one character, what the diff inserts marked `data-skip`; rich blocks go through a small registry (`reader/registry.tsx`: a fence's language or a node type to a React component). Diagrams (TEMPRA-98, tempra-dev `app/diagrams.md`) are its first entry: a `mermaid` fence drawn by Pele (pinned exactly; `reader/Diagram.tsx`, `reader/pele.ts`), loaded lazily, its `style` attributes moved into the CSSOM so the CSP holds (tempra-dev `decisions/diagram-styles-through-cssom.md`), opaque to comments, its source with a quiet notice when it fails; the Worker does not bundle Pele: it checks every mermaid fence on write and import with a small DOM-free checker (`okf/diagrams.ts`: the header against the types Pele draws, a body, and in flowcharts, class, ER and requirement diagrams the quotes and brackets that are structure) and reports a broken one as `diagram_invalid` lint; `worker/test/diagrams.test.ts` holds it to Pele (a dev dependency only), so it never reports what Pele draws. Hover or focus cards over footnote markers and links (footnote markers show the source's number, as the Sources section at the end of the body numbers them), figures (captions, "Figure n.", a broken-image state and a full-screen view with previous and next, Download and Open file to the attachment's page, `reader/Figure.tsx`, `reader/Lightbox.tsx`), and a word diff over `docText` (`@tempra/editor` `diff.ts`) of the changes since human verification or since a chosen version, drawn as `ins`/`del` (a hairline warm rule beside each changed block); the cards and the selection toolbar are popovers in the top layer (`popover="manual"`), placed through `--float-x`/`--float-y`. View Markdown (under the concept's ⋯) shows the file as stored (frontmatter and body, the `GET …/files/{path}` text, what an agent reads; the mono with line numbers) in place of the reader; Copy page copies the same text, Download .md saves it. The reading typography (measure, rhythm, type scale, lists, tables in their own scroll container, code, links, `text-wrap`, figures) is `design/src/prose.css`; cards, highlights and the toolbar are `design/src/reader.css`. The app follows writes live (TEMPRA-12): `GET …/feed` upgrades to a WebSocket held by the Library DO with the hibernation API (`worker/src/feed.ts`), counted once on connect against the caller's request limit and metered as `feed`, and capped (TEMPRA-80): 200 sockets per library, counted in the DO from `getWebSockets()`, and 50 per account across its libraries, leased by a small `AccountFeeds` DO per account (`feed-leases.ts`: at the cap it asks the libraries holding its leases which sockets are still open); a socket over a cap opens and closes at once with code 4029; after each write call the DO pushes the new events. The SPA keeps one socket per library (`app/src/live.ts`), catches up from `GET …/events?since=` after a gap, polls `…/events?since=` instead when a socket is refused with 4029 (trying a socket again after 5 minutes, then less often), shows a pulsing new-version glyph among the concept's tools in the top bar (a notice for a move or delete; swapping in the new version only while the reader is idle), tails Activity and reloads directories in place, and marks what is new since the person last looked: a per-library cursor on the server (`GET`/`PUT …/seen`, TEMPRA-72), which viewing Activity moves forward. The shell's CSP allows the socket (`connect-src 'self' wss://<host>`). A library's pages render in one workspace frame, kept mounted while the person moves within the library. ## Tooling
- **bun for everything JS/TS**: installing (`bun install`, `bun add`), scripts (`bun run …`), tests (`bun test`), one-off binaries (`bunx`). Do not use npm, npx, yarn or pnpm, and do not commit other lockfiles.
- **TypeScript only** on the server (Worker + Durable Object). No Rust or WASM in v1.
- **Biome** for lint and format (`biome.json`); no ESLint or Prettier.
- **cf** (Cloudflare's CLI, beta, pinned) is a dev dependency of `worker/`; run it with `bunx cf …` from `worker/`. The Worker is configured in `worker/cloudflare.config.ts`; there is no `wrangler.jsonc`. To find a command, use `bunx cf cli search "<task>"` (anonymous wording: no names or IDs), then `--help` on the match or `bunx cf schema <command>`; do not walk nested `--help`. cf resource commands take IDs, not names or bindings (scripts/cf.ts reads the D1 ID from the config). Set `CF_SEND_TELEMETRY=false` in scripts and CI. Scripts call cf through `scripts/cf.ts` (async): cf (beta) sometimes prints its result and then never exits (a confirmation prompt keeps it alive, e.g. `d1 migrations apply`), so the helper accepts a complete JSON result once cf goes quiet, and otherwise times out and retries; keep calls made through it safe to repeat.
- **wrangler** stays a dev dependency only as the bundler `cf dev`/`cf build` delegate to (`worker/wrangler.config.ts`). Use Wrangler directly only for what cf lacks: live logs (`bunx wrangler tail tempra`).
- **The site is the exception:** `site/` is configured with `site/wrangler.jsonc`, because Cloudflare Workers Builds (which deploys it and posts PR previews) reads a Wrangler config. It has no bindings or data.

## Testing
- Unit tests run under `bun test`. `cloudflare:workers` does not exist outside workerd, so tests stub it with `mock.module` (see `worker/test/healthz.test.ts`).
- Keep storage and OKF logic free of Worker APIs so it can be tested under bun with `bun:sqlite` standing in for the DO's SQLite handle (`worker/test/sqlite.ts`).
- Bodies are normalized once on their way in, then byte-stable (tempra-dev: decisions/structured-documents). `editor/editor.test.ts` checks every concept body in `fixtures/`: normalizing twice changes nothing, the canonical form parses to the same tree, and the document's text has every textblock in place; plus raw constructs, link rules and the word diff. `editor/reconcile.test.ts` checks block IDs through edits, inserts, deletes, moves and the app's hints. `app/reader.test.tsx` draws every fixture concept with the reader into a DOM (happy-dom): every textblock at its `docText` offset and reading as its text, every block ID drawn once, offsets through DOM points and back (atoms included), selections to the quotes anchors store, the diff leaving the counting alone; plus unsafe links, escaping, raw HTML as code, markers and headings. A failing fixture is a bug in the reader, not a fixture to skip.
- `app/app.test.ts` checks the SPA's router against the server's URLs, `app/live.test.ts` the feed client (replay after loading, catch-up, restore); the gate drives the SPA in Chromium (`playwright-core`, browser from `CHROME_PATH`, the container's `/opt/pw-browsers/chromium`, or `/usr/bin/google-chrome` on CI runners).
- Route and MCP tests (`worker/test/api.test.ts`, `mcp.test.ts`) run the real app in process via `worker/test/harness.ts`: a bun:sqlite store behind the same `callStore` the DO uses, the real account SQL and migrations on bun:sqlite (`worker/test/d1.ts`), an in-memory blob store and fixed test tokens. `s.app` is signed in as the demo library's owner (`owner/demo`), `s.anon` has no session, `s.stranger()` makes a second account. MCP tests drive it with the SDK's own client.
- Tenancy (`worker/test/tenancy.test.ts`) walks every registered `{owner}/{lib}` route as a stranger and expects 404. A new library route needs nothing extra to be covered, but must go through `authorizeLibrary`. Roles (tempra-dev: v2/sharing): `read` reads and comments, `write` also writes content (`requireWrite`) and verifies, the owner alone deletes, restores and runs maintainers (`requireOwner`); comments check `requireComment`, not write. The same file walks every state-changing route as a `read` member and expects nothing to land.
- MCP tool descriptions and `INSTRUCTIONS` in `worker/src/mcp/server.ts` carry the agent workflow; keep them in step with `skills/okf/SKILL.md`.
- Diagrams: `worker/test/diagrams.test.ts` (lint on write and import), `app/diagram.test.tsx` (styles through the CSSOM, drawn and failed in a DOM).
- Comments: `worker/test/comments.test.ts` (the store: lifecycle, anchors through edits, moves and deletes, snapshots and reverts untouched, work items, paging, the ledger dump), `comments-api.test.ts` (REST and MCP, refusals, tenancy), `editor/anchor.test.ts` (the resolver).
- `worker/test/oauth.test.ts` drives the OAuth flow as an MCP client would: discovery, DCR, consent (dev sign-in), token with PKCE, MCP calls, revocation, and "Create libraries" (the choice, selected grants reaching what they made and nothing else, REST with an access token). Its helpers are `worker/test/oauth-flow.ts` (`connectApp` connects with given consent choices), also used by the MCP and tenancy tests.
- The DO write transaction must stay synchronous (no awaits); hash with `okf/hash.ts`, not WebCrypto.
- The blob sweep: `worker/test/sweep.test.ts` (a world of libraries, a bucket and a queue drained into the consumer: the 31 days, the first count holding deletion, a library that never answered, restores, deletes, idempotent messages, the listing and the drift scan; and the write path recording uploads and references). `bun scripts/sweep-bench.ts [libraries]` times it at scale. Never delete a blob still referenced: anything unsure keeps the blob.

## Cloudflare
- `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are set in the cloud environment; cf (and wrangler) read them automatically.
- Remote resources: Worker `tempra` on `app.tempra.dev` (custom domain; `workers.dev` is off), D1 `tempra-accounts` (id in `cloudflare.config.ts`), R2 bucket `tempra-blobs`, KV `tempra-oauth`, Queue `tempra-sweep` (binding `SWEEP_QUEUE`, the blob sweep's fan-out, sent and consumed by the Worker; no dead-letter queue, TEMPRA-81). Do not create or delete remote resources without asking.
- Tokens and libraries are managed at `/tokens` and `/` (or `/api/v1/tokens` and `/api/v1/libraries` with a `human:` token). `bun run seed --remote` (from `worker/`) still creates a library and token directly in the deployed D1.
- KV `tempra-oauth` (binding `OAUTH_KV`) holds OAuth clients and grants. The UI signs people in by email link only (Access was removed at the A4 cut-over); `SIGNUP` (a config var: `invite` in production and staging) decides who may create an account, and `bun run admin invite` manages the list. Local dev uses `DEV_SIGNIN=1` and `SIGNUP=open` from `worker/.dev.vars` (copy `worker/.dev.vars.sample`): sign-in links show on the page for localhost.
- `cloudflare.config.ts` is a function of `--mode`: production by default, `staging` for a separate Worker (`tempra-staging` on `staging.tempra.dev`) with its own D1 `tempra-accounts-staging`, R2 `tempra-blobs-staging`, KV `tempra-oauth-staging`, Queue `tempra-sweep-staging`, metering to `tempra_usage_staging` and rate-limit namespaces 2001, 2002 and 2003 (TEMPRA-76), and `preview` for PR N (`previewDeployment`: `tempra-pr-N` on `pr-N.tempra.dev` with `-pr-N` resources (Queue `tempra-sweep-pr-N` too), ids from `TEMPRA_PR`, `TEMPRA_PREVIEW_D1_ID`, `TEMPRA_PREVIEW_KV_ID`; no cron; metering to `tempra_usage_preview`, rate-limit namespaces 3001, 3002 and 3003). Scripts pick the mode from `TEMPRA_MODE`. With no mode (`cf dev`, `cf workers types`, a bare dry run) no custom domain is attached; `bun run deploy` defaults to `--mode production`.
- Mail goes through Cloudflare Email Service: the `EMAIL` binding is added only when `mailFrom` is set for a deployment in `cloudflare.config.ts`, which needs a sending domain onboarded in Cloudflare. Production sends from `noreply@mail.tempra.dev` (`mail.tempra.dev` is onboarded); local dev with `DEV_SIGNIN=1` still shows links on the page instead of mailing them. `OPERATOR_EMAIL` (a Worker secret, so the address stays out of the repo) receives the daily digest and a notice when someone new joins the waitlist (at most 10 a day), and is the only account that can open `/waitlist` to approve or dismiss them.
- Rate limits are `WRITE_LIMITER` (60 writes a minute per account), `REQUEST_LIMITER` (600 requests a minute per token or app) and `SESSION_LIMITER` (`SESSION_REQUESTS_PER_MINUTE` in `cloudflare.config.ts` per browser session, keyed by the session's stored hash: every page, API call and feed upgrade made with the cookie and no token, static files aside; TEMPRA-80; the gate fails if a busy browse uses over a quarter of it), production's on namespaces 1001, 1002 and 1003 (namespaces are account-wide, so each deployment has its own; `worker/test/config.test.ts` checks none is shared). Over a limit is a 429 with `Retry-After`; the SPA waits it out quietly (`api.ts`: reads retry, prefetches skip, what is shown stays); metering writes to the Analytics Engine dataset `tempra_usage`; storage per library is `LIBRARY_STORAGE_MB`.
- The landing page is the Worker `tempra-site` on `tempra.dev` and `www.tempra.dev` (www redirects to the apex). Cloudflare Workers Builds, connected to this repository with root directory `site`, deploys it: `main` runs `wrangler deploy`, other branches run `wrangler preview`, which posts a Preview URL and one per commit on the PR. It does not go through the app's preview/staging/production jobs.
- Naming: the product is Tempra (repository `cldixon/tempra`, `tempra.dev`); OKF names only the file format. The former `okf-service` Workers and their resources were moved and deleted (v2 spec: Move to tempra.dev). Don't introduce `okf-tool`/`okf-service` names.
- `worker/` is the deployable project and must stay self-contained: its own `package.json` with every dependency, nothing imported from outside `worker/` at build time except the `@tempra/design`, `@tempra/app` and `@tempra/editor` workspace packages (the Worker imports only `@tempra/editor/doc`) (CI's standalone job builds `worker/` with `design/`, `editor/` and `app/` alone; `bun install` builds the app's bundle). Nothing in the repository imports Wordgard any more (TEMPRA-99). `site/` takes the same package as `file:../design`, so Workers Builds must watch `design/*` as well as `site/*`. `cloudflare.config.ts` must not import Worker code (scripts import it under bun).

## CI
`.github/workflows/ci.yml` runs on PRs and pushes to `main`: `bun run check`, `bun run gate` (cf dev, sample-bundle round-trip, UI pages, the SPA and its reader in Chromium, MCP smoke), and a standalone build of `worker/` copied with `design/`, `editor/` and `app/` (`cf deploy --dry-run`). All must pass before merging.

CD (tempra-dev: `delivery/ci-cd.md`) runs after those three, each stage off until its repository variable is `on`:
- `PREVIEWS`: the `preview` job brings up PR N's preview and comments its URL; `preview-cleanup.yml` tears it down when the PR closes and sweeps leftovers nightly.
- `STAGING_DEPLOYS`: every push to `main` deploys staging and checks it (`/healthz`, MCP smoke with secret `STAGING_MCP_TOKEN` if set).
- `PRODUCTION_DEPLOYS`: then production in the same run, with no approval step (tempra-dev: `decisions/production-without-approval.md`); the GitHub Environment `production` has no required reviewer, and adding one would bring the step back.
- Each push to `main` runs on its own (TEMPRA-18): one run never blocks the next, and deploy jobs deploy only the tip of `main` (a superseded commit skips itself).

The `site/ builds` job checks, tests and builds the landing page; its previews and deploys come from Workers Builds.

Secrets: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `PREVIEW_EMAIL` (the operator, seeded as each preview's account), optional `STAGING_MCP_TOKEN`, `PRODUCTION_MCP_TOKEN` (read-only smoke), optional `ANTHROPIC_API_KEY` (only the preview job's `preview up` step sees it, and sets it on the `tempra-pr-N` Worker as a secret through Cloudflare's API; the managed-agent spike, TEMPRA-67), optional `PREVIEW_SEED_TOKEN` (a read-only token on the seed library, only for the `preview up` step, with repository variables `PREVIEW_SEED_LIBRARY` and optional `PREVIEW_SEED_URL`; TEMPRA-109).
