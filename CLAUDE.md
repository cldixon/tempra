# CLAUDE.md

## Spec
The source of truth for Tempra's design, decisions and current state is the Tempra library
**`cl_dixon/tempra-dev`**, read and written over the Tempra MCP tools (`start` with
`library: "cl_dixon/tempra-dev"`). Its `guide.md` says what belongs there; `v2/` is the managed
service as built, `delivery/` is CI/CD, `decisions/` records why, `process/workflow.md` is how a
change goes from a Linear issue to production. Read the concepts a feature touches before starting
on it. When implementation shows a concept is wrong, update the concept first, then the code.

OKF semantics, the store, the ledger and the MCP tools are still specified in the v1 Claude Doc,
**OKF Knowledge Service — Spec** (https://claude.ai/artifact/KMuKyyFBSJHzukyEGqvUDn), until they are
carried over. The v2 Claude Doc is retired (carried over at rev 20). There is no markdown copy of
either in this repo; do not add one.

## UI
The app and the landing page share one design system, `design/` (`@tempra/design`, TEMPRA-8): tokens as CSS custom properties (`--tempra-*`, light and dark through `light-dark()`), a base stylesheet and `.prose` for rendered markdown. Edit `design/src/*.css`, then `bun run build` in `design/` to regenerate `design/dist/` (committed; a test fails if it is stale). The app serves it at a hashed path (`/_design/tempra.<hash>.css`, `style-src 'self'`) and links it from every page; the site imports `@tempra/design/tempra.css`. Visual changes go in the package, not in either consumer.

Minimal and barebones first, in the app and on the site (spec: tempra-dev `v2/design-system.md`, UI rule). This is about styling, not technology: light neutral surfaces, dark text, clear links, pill buttons for actions, no design flourish and no colour until the palette (TEMPRA-1), and as little text as works (headings, labels, links, short sentences), so the bones of what we build stay visible. Scripts, TypeScript, React components and client-side state are fine where a page needs them; the app is becoming a React SPA (TEMPRA-9). Every visual decision comes from `@tempra/design` (tokens, base CSS, and layout primitives and components as they are needed); neither consumer adds styling beyond its own page layout, and nothing is styled inline. The look comes from a separate design effort (TEMPRA-1) working in the package.

The app is a React SPA, `app/` (`@tempra/app`, TEMPRA-9, TEMPRA-14). Every page (library list, directory, concept, ledger, diff, work queue, import and export, recovery, revert and restore, connect, delete, and the account's welcome, connect, tokens, connected apps and account pages) is one shell from the Worker (`worker/src/ui/spa.ts`): the design stylesheet, the bundle at a hashed path (`/_app/app.<hash>.js`, immutable) and an empty root, under a CSP of `script-src 'self'` and `style-src 'self' 'nonce-…'` (a per-response nonce, for Wordgard later); no inline scripts or styles. The server still checks sign-in and, for library pages, `authorizeLibrary` before answering with the shell. The SPA reads everything from the REST API with the session cookie (writes pass `fromThisSite`); `useLoad` (`app/src/api.ts`) keeps what each page loaded (the last 100), so a page seen before draws at once and is checked again in the background, changing only if the answer did, and a concept is prefetched when hovered in the tree or selected in the switcher (`prefetch.ts`); `GET …/files/{path}` with `Accept: application/json` describes any file (a concept with its frontmatter and body as a tree, a synthesized file's tree, an attachment's size and type). Concept bodies are drawn by the reader: Wordgard, read-only, through `@tempra/editor` (TEMPRA-10, TEMPRA-11), with footnote and link tooltips (footnote markers show the source's number, as the Contents & sources panel numbers them), a table of contents and a word diff of the changes since human verification; a Markdown toggle beside Edit in the cluster shows the file as stored (frontmatter and body, the `GET …/files/{path}` text, what an agent reads) in place of the reader. Wordgard's look comes from `@tempra/design` (`design/src/reader.css` sets its `--wg-*` variables); its runtime styles use the shell's nonce. The app follows writes live (TEMPRA-12): `GET …/feed` upgrades to a WebSocket held by the Library DO with the hibernation API (`worker/src/feed.ts`), counted once on connect against the caller's request limit and metered as `feed`; after each write call the DO pushes the new events. The SPA keeps one socket per library (`app/src/live.ts`), catches up from `GET …/events?since=` after a gap, shows a pulsing new-version glyph in the concept's cluster (a notice for a move or delete; swapping in the new version only while the reader is idle), tails the ledger and reloads directories in place, and marks what is new since the last visit (local storage). The shell's CSP allows the socket (`connect-src 'self' wss://<host>`). A library's pages render in one workspace frame (TEMPRA-19, take 2 in TEMPRA-53, tempra-dev `app/workspace.md`; `app/src/Workspace.tsx`; the design handoff is `design/handoff/layout-take-2/`), kept mounted while the person moves within the library: a soft ground with a header (Tempra / the library's menu: switch library and its settings, Import & export, Recovery, Connect, Delete; the avatar's menu: Connect an agent, Tokens, Connected apps, Account, Sign out), a sidebar on the ground (a search pill opening the quick switcher, also Ctrl/Cmd+K) with the file tree (`Tree.tsx`: the whole index from one `GET …/outline` (every file's path, kind, title and seq, no bodies), so opening a folder never waits; a folder's row opens and closes it in place and is not a page; open folders remembered per library; refreshed from the feed shortly after a write and at most every 3 s while writes keep coming; marks for agents' recent changes and changes since the last visit) and the library's two views (Ledger with the head seq, Work queue with its count), the open page as a floating sheet, and on a concept one panel at a time beside the sheet, opened from a control cluster at the sheet's top right (new version, Edit, Markdown; Comments, Review (trust, Verify, changes since verification, the type and any status or staleness set, lint and work), Contents & sources, History (the verification line, the versions, links to the ledger and the raw file), Properties (the frontmatter, the form while editing)); pages draw it through `PanelHost` and `usePanels`, the open panel is remembered and Escape closes it. Chrome (glyphs, menus, the avatar) is `app/src/chrome.tsx`. Under 1100px the panel overlays the sheet; under 900px the sidebar is a drawer behind a Files button (Escape or a tap elsewhere closes it). Comments (TEMPRA-13, tempra-dev `app/comments.md`; `app/src/Comments.tsx`): threads on a concept, optionally on a quoted range of its body, are `comment` events in the ledger (the event's meta carries the action in full; schema v4's `threads` and `comments` tables are derived, with a partial index on open threads) that never change the concept's hash or version; snapshots, diffs and reverts skip them. Anchors are a block ID and an offset into the document's text plus a quote selector (`@tempra/editor/doc`, shared by the Worker and the app), resolved against the body being shown when read, never rewritten on write; an agent's quote is markdown as `read` shows it, matched by the text it reads as. Selecting text in the reader shows a small selection toolbar (a Wordgard tooltip; Comment for now) that goes when the selection does; Comment starts a draft, filled grey in the body until it is posted, cancelled or left empty. Comment styling is lines and greys only (underlines, rules, the selection grey; no color). Open threads are underlined (Wordgard range decorations, `Reader.highlight`), reload when the feed carries a comment event, and are counted in the tree; agents use the `comments` and `comment` MCP tools, and open threads are `comment` items in `work`. Editing (TEMPRA-15, tempra-dev `app/editor.md`; `app/src/Editor.tsx`, `useEditing` in `pages/File.tsx`): Edit turns the same reader editable (a Wordgard compartment; `editor/src/edit.ts`: menu bar, history, the GFM blocks and marks, a link dialog on Ctrl/Cmd+K (there instead of the switcher) offering the library's paths and refusing unsafe schemes, images pasted or dropped uploaded beside the concept); the frontmatter is a form in the Properties panel (stamped fields shown, never sent); a sticky bar at the sheet's top holds the note, Save and Cancel; Save needs a one-line note and sends `PUT …/files/{path}` with `If-Match`, then shows the lint. While editing, the page's concept is frozen (a write by someone else shows the banner, never swaps in), and leaving with unsaved edits asks first (router leave guard, `beforeunload`). A 412 fetches the version there now and merges block by block (block order by ID with diff3, then each block's content; `@tempra/editor` `merge.ts`) and field by field; changes to different blocks combine, a block both changed is picked in the merge view. Account pages sit on the same ground in a centred 720px column under a header of Tempra and the avatar's menu. The library's root opens with no document (one line of counts and a link to the root index.md); a folder's URL, reached from links and crumbs, shows the folder's synthesized index.md in the reader, never a second listing of what the tree already shows. Icons are Lucide's (`lucide-react`, 16px, stroke 1.5) through `Icon` in `chrome.tsx`. The layout's CSS is `design/src/workspace.css`; tokens (take 2: greys, fonts, type scale, radii, shadow; no colour until TEMPRA-1) are `design/src/tokens.css`. Three things stay server-rendered on purpose, as security-critical pages that must work with no script: sign-in (`signin.ts`), app consent (`/authorize`, `oauth/`) and the email-change link (`/account/email/confirm`). Downloads (raw markdown, attachments, exports) are server routes too. Account management is in the API (`account-api.ts`: account, sessions, email, handle, delete, connected apps), for a signed-in session only, never a token. Terms and privacy live on the landing page (`tempra.dev/terms`, `/privacy`); the app's old URLs redirect there.

The landing page (`site/`) is Astro: semantic HTML, the design package plus one small layout stylesheet, no web fonts or third-party scripts.

## Tooling
- **bun for everything JS/TS**: installing (`bun install`, `bun add`), scripts (`bun run …`), tests (`bun test`), one-off binaries (`bunx`). Do not use npm, npx, yarn or pnpm, and do not commit other lockfiles.
- **TypeScript only** on the server (Worker + Durable Object). No Rust or WASM in v1.
- **Biome** for lint and format (`biome.json`); no ESLint or Prettier.
- **cf** (Cloudflare's CLI, beta, pinned) is a dev dependency of `worker/`; run it with `bunx cf …` from `worker/`. The Worker is configured in `worker/cloudflare.config.ts`; there is no `wrangler.jsonc`. To find a command, use `bunx cf cli search "<task>"` (anonymous wording: no names or IDs), then `--help` on the match or `bunx cf schema <command>`; do not walk nested `--help`. cf resource commands take IDs, not names or bindings (scripts/cf.ts reads the D1 ID from the config). Set `CF_SEND_TELEMETRY=false` in scripts and CI. Scripts call cf through `scripts/cf.ts` (async): cf (beta) sometimes prints its result and then never exits (a confirmation prompt keeps it alive, e.g. `d1 migrations apply`), so the helper accepts a complete JSON result once cf goes quiet, and otherwise times out and retries; keep calls made through it safe to repeat.
- **wrangler** stays a dev dependency only as the bundler `cf dev`/`cf build` delegate to (`worker/wrangler.config.ts`). Use Wrangler directly only for what cf lacks: live logs (`bunx wrangler tail tempra`).
- **The site is the exception:** `site/` is configured with `site/wrangler.jsonc`, because Cloudflare Workers Builds (which deploys it and posts PR previews) reads a Wrangler config. It has no bindings or data.

## Testing
- Unit tests run under `bun test`. `cloudflare:workers` does not exist outside workerd, so tests stub it with `mock.module` (see `worker/test/healthz.test.ts`).
- Keep storage and OKF logic free of Worker APIs so it can be tested under bun with `bun:sqlite` standing in for the DO's SQLite handle (`worker/test/sqlite.ts`).
- Bodies are normalized once on their way in, then byte-stable (tempra-dev: decisions/structured-documents). `editor/editor.test.ts` checks every concept body in `fixtures/`: normalizing twice changes nothing, the canonical form parses to the same tree, the tree survives Wordgard and back (block IDs included), and the reader's text runs sit where the document's text has them; plus raw constructs, unsafe links, escaping, text offsets and the word diff. `editor/reconcile.test.ts` checks block IDs through edits, inserts, deletes, moves and the app's hints. A failing fixture is a bug in the bridge, not a fixture to skip.
- `app/app.test.ts` checks the SPA's router against the server's URLs, `app/editor.test.ts` the frontmatter form, link targets and the merge's start, `editor/merge.test.ts` the three-way merge, `app/live.test.ts` the feed client (replay after loading, catch-up, restore); the gate drives the SPA in Chromium (`playwright-core`, browser from `CHROME_PATH`, the container's `/opt/pw-browsers/chromium`, or `/usr/bin/google-chrome` on CI runners).
- Route and MCP tests (`worker/test/api.test.ts`, `mcp.test.ts`) run the real app in process via `worker/test/harness.ts`: a bun:sqlite store behind the same `callStore` the DO uses, the real account SQL and migrations on bun:sqlite (`worker/test/d1.ts`), an in-memory blob store and fixed test tokens. `s.app` is signed in as the demo library's owner (`owner/demo`), `s.anon` has no session, `s.stranger()` makes a second account. MCP tests drive it with the SDK's own client.
- Tenancy (`worker/test/tenancy.test.ts`) walks every registered `{owner}/{lib}` route as a stranger and expects 404. A new library route needs nothing extra to be covered, but must go through `authorizeLibrary`.
- MCP tool descriptions and `INSTRUCTIONS` in `worker/src/mcp/server.ts` carry the agent workflow; keep them in step with `skills/okf/SKILL.md`.
- Comments: `worker/test/comments.test.ts` (the store: lifecycle, anchors through edits, moves and deletes, snapshots and reverts untouched, work items, paging, the ledger dump), `comments-api.test.ts` (REST and MCP, refusals, tenancy), `editor/anchor.test.ts` (the resolver).
- `worker/test/oauth.test.ts` drives the OAuth flow as an MCP client would: discovery, DCR, consent (dev sign-in), token with PKCE, MCP calls, revocation.
- The DO write transaction must stay synchronous (no awaits); hash with `okf/hash.ts`, not WebCrypto.

## Cloudflare
- `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are set in the cloud environment; cf (and wrangler) read them automatically.
- Remote resources: Worker `tempra` on `app.tempra.dev` (custom domain; `workers.dev` is off), D1 `tempra-accounts` (id in `cloudflare.config.ts`), R2 bucket `tempra-blobs`, KV `tempra-oauth`. Do not create or delete remote resources without asking.
- Tokens and libraries are managed at `/tokens` and `/` (or `/api/v1/tokens` and `/api/v1/libraries` with a `human:` token). `bun run seed --remote` (from `worker/`) still creates a library and token directly in the deployed D1.
- KV `tempra-oauth` (binding `OAUTH_KV`) holds OAuth clients and grants. The UI signs people in by email link only (Access was removed at the A4 cut-over); `SIGNUP` (a config var: `invite` in production and staging) decides who may create an account, and `bun run admin invite` manages the list. Local dev uses `DEV_SIGNIN=1` and `SIGNUP=open` from `worker/.dev.vars` (copy `worker/.dev.vars.sample`): sign-in links show on the page for localhost.
- `cloudflare.config.ts` is a function of `--mode`: production by default, `staging` for a separate Worker (`tempra-staging` on `staging.tempra.dev`) with its own D1 `tempra-accounts-staging`, R2 `tempra-blobs-staging` and KV `tempra-oauth-staging`, and `preview` for PR N (`previewDeployment`: `tempra-pr-N` on `pr-N.tempra.dev` with `-pr-N` resources, ids from `TEMPRA_PR`, `TEMPRA_PREVIEW_D1_ID`, `TEMPRA_PREVIEW_KV_ID`; no cron; metering to `tempra_usage_preview`). Scripts pick the mode from `TEMPRA_MODE`. With no mode (`cf dev`, `cf workers types`, a bare dry run) no custom domain is attached; `bun run deploy` defaults to `--mode production`.
- Mail goes through Cloudflare Email Service: the `EMAIL` binding is added only when `mailFrom` is set for a deployment in `cloudflare.config.ts`, which needs a sending domain onboarded in Cloudflare. Production sends from `noreply@mail.tempra.dev` (`mail.tempra.dev` is onboarded); local dev with `DEV_SIGNIN=1` still shows links on the page instead of mailing them. `OPERATOR_EMAIL` (a Worker secret, so the address stays out of the repo) receives the daily digest and a notice when someone new joins the waitlist (at most 10 a day), and is the only account that can open `/waitlist` to approve or dismiss them.
- Rate limits are `WRITE_LIMITER` (60 writes a minute per account) and `REQUEST_LIMITER` (600 requests a minute per token or app); metering writes to the Analytics Engine dataset `tempra_usage`; storage per library is `LIBRARY_STORAGE_MB`.
- The landing page is the Worker `tempra-site` on `tempra.dev` and `www.tempra.dev` (www redirects to the apex). Cloudflare Workers Builds, connected to this repository with root directory `site`, deploys it: `main` runs `wrangler deploy`, other branches run `wrangler preview`, which posts a Preview URL and one per commit on the PR. It does not go through the app's preview/staging/production jobs.
- Naming: the product is Tempra (repository `cldixon/tempra`, `tempra.dev`); OKF names only the file format. The former `okf-service` Workers and their resources were moved and deleted (v2 spec: Move to tempra.dev). Don't introduce `okf-tool`/`okf-service` names.
- `worker/` is the deployable project and must stay self-contained: its own `package.json` with every dependency, nothing imported from outside `worker/` at build time except the `@tempra/design`, `@tempra/app` and `@tempra/editor` workspace packages (the Worker imports only `@tempra/editor/doc`) (CI's standalone job builds `worker/` with `design/`, `editor/` and `app/` alone; `bun install` builds the app's bundle). The Worker imports no Wordgard: never `@tempra/editor` itself or `@tempra/editor/view`. `site/` takes the same package as `file:../design`, so Workers Builds must watch `design/*` as well as `site/*`. `cloudflare.config.ts` must not import Worker code (scripts import it under bun).

## CI
`.github/workflows/ci.yml` runs on PRs and pushes to `main`: `bun run check`, `bun run gate` (cf dev, sample-bundle round-trip, UI pages, the SPA and its reader in Chromium, MCP smoke), and a standalone build of `worker/` copied with `design/`, `editor/` and `app/` (`cf deploy --dry-run`). All must pass before merging.

CD (tempra-dev: `delivery/ci-cd.md`) runs after those three, each stage off until its repository variable is `on`:
- `PREVIEWS`: the `preview` job brings up PR N's preview and comments its URL; `preview-cleanup.yml` tears it down when the PR closes and sweeps leftovers nightly.
- `STAGING_DEPLOYS`: every push to `main` deploys staging and checks it (`/healthz`, MCP smoke with secret `STAGING_MCP_TOKEN` if set).
- `PRODUCTION_DEPLOYS`: then production in the same run, with no approval step (tempra-dev: `decisions/production-without-approval.md`); the GitHub Environment `production` has no required reviewer, and adding one would bring the step back.
- Each push to `main` runs on its own (TEMPRA-18): one run never blocks the next, and deploy jobs deploy only the tip of `main` (a superseded commit skips itself).

The `site/ builds` job checks, tests and builds the landing page; its previews and deploys come from Workers Builds.

Secrets: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `PREVIEW_EMAIL` (the operator, seeded as each preview's account), optional `STAGING_MCP_TOKEN`, `PRODUCTION_MCP_TOKEN` (read-only smoke).
